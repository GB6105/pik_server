# ADR-0033: 이후 단계 정책 제안 (구독 처리량·분석 측정·OCR·검색·사진 수렴·보관·알림)

- 상태: 일부 채택 (Codex 비판 검토 R1~R8 수렴, 2026-11-01). #1 RevenueCat 요금제 채택 (D-12 해소). #2·#3 (임시 기준)·#4·#10·#11 사용자 결정으로 채택 (2026-11-01, D-27 해소). #5~#9는 제안 (측정·외부 확인 대기)
- 날짜: 2026-11-01
- 관련: FR-B-03·04·05, FR-I-01·03, FR-S-01·02, FR-A-02·04, FR-L-05, FR-N-02, ADR-0016, ADR-0017, ADR-0018, ADR-0019, ADR-0020, ADR-0022, ADR-0024 #9-3·#12-1, ADR-0031, 설계 문서 `docs/design/later-stage-policies.md`

## 맥락
- 단계 6 이후에 필요한 미결 결정 (D-07·D-08·D-09·D-12·D-14·D-20)과 미정 정책 (P02·P03·P08·P09·P10·P11)을 Codex와 검토했다.
- 사용자가 확정한 결정 (Haiku 5.5, RevenueCat, 검색 Basic = Jev·Pro = Jev+LLM, 서버 중심 알림)은 바꾸지 않는다.
- 세부 계약 (지급·병합 규칙, 측정 조건·지표, 보관 타이머, 발송 제한)은 설계 문서 `docs/design/later-stage-policies.md`에 둔다. 이 ADR은 요약이며, 둘이 다르면 설계 문서를 기준으로 이 ADR을 고친다.

## 근거
- 2: REST의 Pro=true만으로 지급하면 복원·TRANSFER로 초기량을 반복해서 받을 수 있다. 확인되지 않은 만료로 거절하면 RevenueCat 장애가 유료 사용자를 막는다 (FR-B-05).
- 3: 장당 비용 $0.00058~0.00081 (Messages, 2026-11-01 추정), Batch는 절반. 손익표는 스토어 15%/30%와 RevenueCat 1%를 넣었다.
- 5: 독립 300건에서 오판 0건이면 오판율의 단측 95% 상한은 약 0.99%다. 모두 `NEEDS_CHECK`로 두어 오판율만 낮추는 설정은 coverage 하한으로 불합격시킨다.
- 4: 막는 방법 (구매 식별값의 HMAC을 탈퇴 뒤에도 보관)은 정상적으로 돌아온 사용자의 초기량도 막고 (기존 사진 3,000장 재분석에 하루 100장씩 약 30일), 탈퇴 최소 기록·동의 안내·법률 검토 범위를 넓힌다. 남용해도 사용자는 구독료를 계속 내며, 탈퇴할 때마다 메모·태그·분석 결과를 모두 잃는다.
- 10: iOS·Android·Google 포토의 휴지통은 모두 30일이다 (2026-11-01 확인). 서버의 삭제 감지는 실제 삭제보다 늦으므로 여유 5일을 더했다. 30일 안에 복원했어도 35일 뒤에 접속하면 메타데이터를 잃을 수 있으므로 고지한다.
- 11 P02: 사용자 지시 "정책 자체를 SSOT에 맞게 다시 수정"에 따라 FR-S-01 권한 문구 ("무료는 체험 대상, Pro는 전체 접근 가능 사진")를 그대로 따른다. 만료자는 무료 사용자이므로 체험 대상 범위가 적용된다. FR-S-02·FR-B-05의 "만료 시 기초 검색 유지"는 무료 기초 검색을 계속 제공한다는 뜻으로 읽는다. 만료자의 기존 분석 결과는 삭제하지 않고, 기존 액션·이벤트 조회는 유지한다.
- 11 P02: 검색은 단말이 실행하므로 범위 제한은 단말만 적용할 수 있다. 앱을 변조하면 우회할 수 있지만 자기 기기 안의 검색 범위만 넓어지고 서버 비용은 바뀌지 않으므로 수용한다 (ADR-0017).
- 11 P02 (R16): 체험 대상을 차감 이력으로 정하면 수렴·귀속·대표 교체 뒤에도 근거가 남는다. Pro 접수가 체험을 쓰면 Pro 사용자가 체험 시작·DeviceCheck·assertion 흐름을 타므로 쓰지 않는다. 기존 계정 귀속에서 합산하면 계정의 체험 범위가 100장을 넘는다.
- 11 P09 (R16): 종류별 예약의 중복 방지만으로는 일 상한을 지킬 수 없어 (기기, 날짜) 슬롯으로 직렬화한다. 비로그인 때 단말이 쓴 횟수를 인계하지 않으면 로그인 직후 다시 발송한다. 로컬 리마인드와 서버 일정 알림의 경로 간 묶음은 공통 식별자·표시 담당 합의가 필요해 첫 출시에서 제외한다.
- 11 P09: 상한을 기기 기준으로 센다. 정리 독려를 대상이 남은 기기에 모두 보내기로 했으므로 (ADR-0024 #12-1), 주체 기준으로 세면 두 번째 기기의 알림이 막힌다. 일정에 묶인 알림을 상한으로 막으면 사용자가 일정을 놓치므로 제외한다.

## 결과
- 사용자 결정 반영 (2026-11-01): P02·P08·P11 확정, P03·P09·P10 일부 확정 (`open-policies.md`), D-27 해소. 결정 과정과 Claude 추천과 다른 선택은 근거·대안 표에 적었다.
- 남은 사용자 결정: P03 정가 (임시 기준 $8), 탈퇴 최소 기록 보관 기간 (법률 검토), P09 이벤트 알림 선행 시간·장소 반경, P10 태그 정규화·AND/OR·전역 편집·앨범 정렬 (FR-L 구현 설계에서 제안).
- 외부 확인 대기: D-08 (Jev 서면 확인), D-20 (FR-A-04 실기기 검증), D-07 (측정).
- 출처: 사용자는 항목마다 AskUserQuestion으로 선택지를 보고 정했다 (2026-11-01). D-27·P02는 설명을 다시 요청한 뒤 정했고, P02는 처음 고른 안 (만료자 기존 결과 전체)을 SSOT 보고 뒤 SSOT 기준으로 바꿨다. P09 정리 독려의 기준 시점·단계 초기화 규칙과 일 발송 상한의 기기 기준·우선순위는 Claude가 제시하고 사용자가 이의 없이 결정했다. 같은 시각 묶음을 같은 발송 경로 안으로 좁힌 것은 Codex R17 지적 뒤 사용자가 따로 승인했다.
