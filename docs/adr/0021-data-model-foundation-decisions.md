# ADR-0021: 데이터 모델 기반 결정 (사진 식별·묶음·이용량·동의·원본 삭제)

- 상태: 채택
- 날짜: 2026-10-26
- 관련: FR-A-04, FR-B-01, FR-G-01, FR-I-01~03, FR-L-01, FR-L-06, FR-O-02, P01, P05, P07, P08, P11, ADR-0016, ADR-0017, ADR-0020, D-09, D-14, 브랜치 `feature/first-fr-plan`

## 맥락
- 구현 순서를 정하기 전에, 나중에 바꾸면 데이터 모델·API·아키텍처를 다시 고쳐야 하는 미결 항목을 먼저 정한다.
- 값만 다른 항목 (P02·P03 수치, P05 임계값, P09, P10, 보관 기간)은 설정값으로 두고 이 ADR에서 다루지 않는다.
- 이미 정해진 항목: 동기화 충돌 = `CONFLICT` + 현재 버전 반환 (FR-L-05), Pro 처리량 형태 = 최초·일별 처리량 (FR-I-01).

## 결정 (모두 사용자 결정)
| # | 항목 | 결정 |
|---|---|---|
| 1 | 사진 식별 키 (P07, FR-A-04) | 단말이 사진을 처음 발견할 때 Pik `photoId` (UUID)를 만든다. (기기, OS 로컬 ID) 매핑은 별도로 둔다. 다른 기기에서는 지문 (촬영 시각·픽셀 크기·지각 해시, iOS끼리는 PHCloudIdentifier 후보)으로 매칭하며, 지문 항목은 FR-A-04 기술 검증에서 정한다. 서버는 `photoId`만으로 소유를 인정하지 않고 (주체, `photoId`)로 검증한다 |
| 2 | 묶음·대표 판단 위치 (P05, D-09) | 단말이 사진별 촬영 시각과 유사도 벡터 (모델 ID·버전 포함)를 보내고 서버가 묶음·대표를 정한다. 같은 모델·버전의 벡터끼리만 비교한다. 단말은 대표 사진의 축소본만 올린다 |
| 3 | 이용량 차감 (P01) | 접수할 때 묶음의 대표+구성 사진 수만큼 예약하고, 분석이 실패하면 반환한다. 같은 사진 버전의 재분석은 차감하지 않는다 |
| 4 | 분석 파이프라인 (D-14) | ADR-0016 구조를 확정한다: S3 presigned 직접 업로드, PostgreSQL 작업 큐 (`SKIP LOCKED`), 대량 백로그는 Message Batches. 접수 단계는 아래처럼 바뀐다 |
| 5 | 동의 철회 (P08) | 전송 전 작업을 취소하고 새 전송을 막는다. 이미 보낸 요청의 응답은 저장하지 않는다. 이미 만든 분석 결과·액션·이벤트는 유지한다 |
| 6 | 동의 단위 (D-14) | 동의 하나로 사진 분석과 검색어 전송을 함께 받는다. 거절하면 자연어 검색도 제공하지 않는다. 동의 기록에는 목적 필드를 두어 목적별 동의로 바꿀 수 있게 한다 |
| 7 | OS 원본 삭제 후 메타데이터 (P11) | 원본 삭제가 확인되면 '원본 없음' 상태로 보존하고, 보관 기간 (설정값)이 지나면 삭제한다. OS '최근 삭제'에서 복구되면 다시 연결한다. 권한 철회·다운로드 불가·기기 미보유는 삭제로 보지 않고 상태로만 표시한다 |
| 8 | 체험 집계 단위 (ADR-0020 파생 규칙) | 체험 이용량을 기기와 계정에 모두 기록하고, 하나라도 소진했으면 체험을 주지 않는다. 새 계정으로 로그인하면 그 기기의 게스트 이용량을 이어받는다. 기기·제공자 식별자는 서버 비밀 키 HMAC으로만 저장한다 |

### 분석 접수 흐름 (ADR-0016 파이프라인 1단계 대체)
1. 접수: `POST /analysis-jobs` (`Idempotency-Key`, 사진별 `photoId`·사진 버전·촬영 시각·유사도 벡터)
2. 서버가 시간대와 유사도로 묶음·대표를 정한다 (임계값은 P05 설정값)
3. 작업·묶음·이용량 예약 (대표+구성)·멱등 기록을 한 트랜잭션에 저장한다
4. 202 + 작업 ID + 진행 상태 + 묶음 구성 + 대표 사진에만 S3 presigned PUT URL을 반환한다
- 이후 업로드·실행·후속 처리는 ADR-0016 2~6단계와 같다.

## 근거
- 1: 요구사항 140행 ("Pik의 photoId와 기기별 OS 사진 식별자를 분리하며 같은 사진의 다른 기기 ID는 별도 매칭")과 같은 구조다. 비로그인 메타데이터는 기기에 둔다는 142행 때문에, 오프라인에서도 ID를 붙일 수 있는 단말 생성만 성립한다.
- 2: FR-I-02는 판단 쪽이 "개별 시간·시각적 유사 정보"를 받고 서버가 묶음 구성·버전을 저장하는 구조다. P05가 미정이라 규칙을 서버 설정으로 조정할 수 있어야 한다. 서버가 묶음 구성을 알아야 3의 대표+구성 예약도 서버 기준으로 계산된다.
- 3: FR-I-01의 "동시 요청의 한도 예약과 실제 완료 집계를 구분"과 같다. 원문 설계 가정 (대표·구성 합계)을 따른다.
- 5: 시나리오 G-01의 "미동의·한도 소진은 신규 분석을 중단하고 기존 결과를 유지"와 같은 처리다.
- 6: 원문 FR-O-02는 동의 하나로 표현한다. 목적 필드는 이후 변경 비용을 줄인다.
- 7: FR-L-06은 OS '최근 삭제'를 영구 삭제로 보지 않고, 요구사항 1179행은 권한 철회 등을 원본 삭제와 다르게 처리하라고 한다.
- 8: ADR-0020의 재설치·재가입 체험 재지급 없음을 실제로 지키려면 기기·계정 양쪽 기록이 필요하다.

| 대안 | 버린 이유 |
|---|---|
| 서버 발급 `photoId` | 새 사진마다 서버 등록이 필요해 비로그인 로컬 원칙 (142행)과 충돌 |
| 콘텐츠 해시 키 | 편집·재압축에서 키가 바뀌어 사진 버전 개념과 맞지 않음 |
| OS 로컬 ID 키 | 요구사항 140·948행 위반, 다른 기기 복원 불가 |
| 단말이 묶음 판단 | 원문의 판단 위치와 다르고, P05 규칙 변경에 앱 업데이트 필요 |
| 서버가 이미지로 묶음 판단 | 모든 사진을 올려야 해 전송·저장 비용이 가장 큼 |
| 완료 시 차감 | 동시 접수 때 한도 초과 처리 가능 |
| SQS 큐·API 경유 업로드 | 구성 요소 증가·이중 쓰기, API 인스턴스의 이미지 트래픽 부담 |
| 철회 시 결과 삭제 | 자동 생성 결과와 사용자 수정을 구분 저장해야 하고 처리 규칙이 추가로 필요 |
| 목적별 동의 | 원문의 단일 동의 표현과 다름. 목적 필드로 이후 전환 가능 |
| 원본 삭제 즉시 메타데이터 삭제 | '최근 삭제' 복구 시 정보 손실, 다른 기기에 남은 사진의 정보까지 지울 위험 |
| 계정 기준 체험 집계 | 같은 기기에서 새 계정을 만들면 체험을 다시 받을 수 있음 |

## 결과
- ADR-0016의 파이프라인 (제안)은 확정되고, 접수 단계는 위 흐름으로 바뀐다. ADR-0016·0017의 "동의 거절 시 자연어 검색 비제공 (제안)"은 확정된다. ADR-0020의 파생 규칙은 확정된다.
- D-09는 묶음 판단·대표만 전송까지 해소된다. 단말 OCR 여부와 축소 해상도는 측정 (D-07)과 함께 정한다.
- 단말에는 iOS·Android가 같은 모델·버전의 유사도 벡터를 만드는 구성이 필요하다. 모델 선택은 클라이언트와 합의한다.
- 계속 미정: 유사도 벡터의 서버 보관 범위 (재편성용, P05·P08), 묶음 임계값·대표 선정·재편성 규칙 (P05 설정값), 체험 사진 교체·3회 클릭 집계 (P01), 임시 보관 기간·'원본 없음' 보관 기간 값 (P08·P11 설정값), 이벤트의 모든 사진 제외 시 상태 (P11).
