# ADR-0030: 설계 검토 1차 반영 (동의 철회 판정·멱등 입력 경계·키 교체 절차·SSOT 차이 목록)

- 상태: 채택 (사용자가 Codex 비판 검토와 수정을 지시, 2026-11-01)
- 날짜: 2026-11-01
- 관련: ADR-0016, ADR-0021 #5, ADR-0024 #1, ADR-0026, ADR-0027 #2, ADR-0028, ADR-0029 #12·#18, FR-O-02, FR-B-01, FR-I-01·03, FR-G-01, FR-E-01, 브랜치 `feature/design-review-codex`

## 맥락
- 사용자가 같은 워크스페이스의 Codex에게 지금까지의 기획·설계를 비판적으로 검토받고 수정하라고 지시했다. 기준은 안정성·비용·속도다.
- Codex는 발견 사항 14건 (높음 7, 중간 7)과 설계 누락·SSOT 보고를 냈다. Claude가 주장마다 파일과 코드를 대조했고, 이 ADR은 이미 확정된 설계를 고치는 항목만 다룬다. 단계 5 설계에 속하는 항목은 단계 5 설계 ADR에서 해소한다.

## 결정
| # | 항목 | 결정 |
|---|---|---|
| 1 | 동의 철회 판정 (R1-01) | 현재 동의가 유효한지만 보면 "전송 → 철회 → 재동의 → 응답 도착"에서 철회 전에 보낸 요청의 응답을 저장하게 된다. 그래서 접수할 때 그 시점의 동의 버전 (`ai_consent.version`)을 접수 행에 기록한다. 전송 직전과 결과 저장 직전에는 "현재 동의가 유효함"과 "기준 버전보다 큰 버전의 비동의 결정이 없음"을 함께 확인한다. `ai_consent`는 결정마다 행이 쌓이므로 스키마는 바꾸지 않는다. 결과 저장·전송 판정과 동의 결정 기록은 주체별 트랜잭션 범위 잠금으로 순서를 정한다 (결정 기록 = 배타, 판정 = 공유). 접수 행의 열 추가와 `consent` 모듈 공개 API 확장은 단계 5에서 구현한다 |
| 2 | 체험 비용 상한 문구 (R1-06) | ADR-0024 근거 #1의 "체험 분석 비용 상한 100건"은 **결과를 만든 사진 수**의 상한이다. 실패·취소는 예약을 반환하므로 외부 호출 비용의 상한은 아니다. 호출 시도 예산·전체 호출 속도 예산·일일 비용 한도의 구조는 단계 5-2에서 정한다 |
| 3 | 외부 호출 키의 의미 (R1-04) | `external_call.request_key`는 서버 안에서 같은 호출 의도를 식별하고, Message Batches 결과를 `custom_id`로 매칭하는 값이다. 제공자 쪽 중복 과금을 막거나 잃어버린 동기 응답을 다시 받게 해 주지 않는다 (Anthropic `custom_id`는 한 배치 안의 결과 매칭 ID). 결과를 알 수 없는 호출의 종료 규칙은 단계 5-2에서 정한다 |
| 4 | 일회성 증거와 멱등 입력 (R1-09) | DeviceCheck 토큰처럼 재시도마다 새로 받는 증거는 업무 본문에 넣지 않는다. 분석 접수에서는 요청 헤더 `Device-Check-Token`으로 받고, 멱등 해시는 업무 입력 (사진 목록·사진 버전·묶음 판단 입력)으로만 계산한다. 같은 키의 기록이 있으면 외부 호출 (`recordStart`)과 예약 없이 그 접수의 현재 상태를 돌려준다. 새 접수일 때만 트랜잭션 밖에서 `recordStart`를 호출한다 |
| 5 | Android ID HMAC 키 교체 (R1-10) | 선택 설정 `PIK_USAGE_DEVICE_KEY_ACTIVE` (쓰기 키 버전)를 추가한다. 값이 없으면 지금처럼 가장 큰 버전을 쓴다 (ADR-0029 #12의 기본 동작 유지). 교체는 2단계 배포로 한다. ① 새 키를 목록에 추가하고 활성 버전은 이전 키로 고정해 모든 인스턴스가 두 키로 조회하게 한다 ② 모든 인스턴스가 ①로 바뀐 뒤 활성 버전을 새 키로 바꾼다. 활성 버전이 목록에 없으면 기동을 실패시킨다. 구현은 운영 배포 전 (키 교체 절차와 함께)에 한다 |
| 6 | JWT 서명 키 교체 절차 (설계 누락) | ADR-0027 #2의 교체 (새 개인 키 + 이전 공개 키)를 한 번에 배포하면, 롤링 배포 중 새 키를 모르는 이전 인스턴스가 새 토큰을 거부한다. 그래서 2단계로 한다. ① 새 키를 **공개 키로만** 추가해 배포 ② 모든 인스턴스가 ①로 바뀐 뒤 새 키를 개인 키로, 이전 키를 공개 키로 바꿔 배포 ③ 이전 키로 서명된 토큰이 모두 만료된 뒤 (access 15분 + 여유) 이전 키를 뺀다. 현재 코드 (공개 키 여러 개, 개인 키 1개)로 가능하다 |
| 7 | 승인된 SSOT 차이 목록 (SSOT 보고 3) | 사용자가 승인한 SSOT 차이·해석을 `.claude/docs/ssot-deviations.md` 한 곳에 모은다. 인수 조건과 테스트를 쓸 때 SSOT 원문과 함께 이 목록을 본다 |
| 8 | 마지막 체험 사진의 이벤트 생성 자격 (SSOT 보고 1) | FR-G-01 (31행)은 접수가 허용된 마지막 체험 사진의 파생 결과를 잔여량 0 때문에 버리지 말라고 하고, FR-E-01 (718·728행)은 체험 잔여 범위를 확인하고 소진 시 신규 생성을 중단한다고 한다. 구현은 "이미 허용된 분석의 파생 결과 (이벤트 포함)는 그 접수의 자격을 이어받는다"로 해석한다 (`consistency-rules.md` 구독·결제). SSOT 문구 정리는 사용자에게 보고한다 |

### 단계 5 설계로 넘긴 항목
R1-02 (구성 사진의 개별 근거), R1-03 (실행 세대·조건부 완료), R1-05 (업로드 바이트 고정), R1-07 (이벤트 중복), R1-08 (접수별 항목 판정), R1-11 (실행 모드별 기한), R1-12 (묶음 범위는 5-1 계산 범위), R1-13 (벡터 계약의 한계·정밀도), R1-14 (생성 상태), SSOT 보고 2, 설계 누락 표의 5-1~5-3 행.

## 근거
- 1: ADR-0021 #5는 철회 뒤 이미 보낸 요청의 응답을 저장하지 않는다고 정했다. 현재 `AiConsents.isGranted`는 최신 결정만 본다. 동의 순번 일치만 요구하면 같은 동의를 다시 저장하는 것만으로도 작업이 취소되므로, "기준 버전 이후 비동의 결정 존재"를 검사한다. 비동의 결정은 새 행을 넣으므로 기존 행 잠금으로는 막을 수 없어 주체 단위 잠금을 쓴다.
- 3: Anthropic 배치 생성 API 문서는 `custom_id`를 배치 안의 결과 매칭 ID로 정의한다. Messages API에서 요청 키로 응답을 다시 조회하는 계약은 확인하지 못했다 (Codex 확인, 2026-11-01).
- 4: 멱등 해시는 직렬화한 커맨드 전체로 계산한다 (ADR-0026). 토큰이 본문에 있으면 응답을 잃은 뒤 새 토큰으로 재전송할 때 `IDEMPOTENCY_KEY_REUSED`가 된다.
- 5: 지금은 가장 큰 버전이 쓰기 키다 (`DeviceKeys`). 롤링 배포 중 이전 인스턴스는 새 키로 만든 행을 찾지 못하고 이전 키로 새 행을 만들어, 같은 기기에 체험 기록이 둘 생긴다. 설정이 없을 때의 동작을 그대로 두면 ADR-0029 #12를 바꾸지 않고 교체 절차만 더할 수 있다.
- 6: Codex 설계 누락 지적. `JwtKeys`는 개인 키 1개와 공개 키 여러 개를 받으므로 절차만으로 해결된다.

| 대안 | 버린 이유 |
|---|---|
| 1: 동의 순번이 접수 때와 같을 때만 저장 | 같은 동의를 다시 저장해도 작업이 취소됨 |
| 1: 철회 이벤트로 작업을 즉시 취소 | 이미 보낸 요청의 응답 폐기는 결국 저장 직전 검사가 필요함. ADR-0028은 철회 이벤트를 두지 않음 |
| 4: 토큰을 본문에 두고 해시에서만 제외 | 커맨드마다 제외 필드를 관리해야 하고, 실수하면 같은 결함이 재발함 |
| 5: 키 교체 중 설치 등록 일시 중지 | 설치 가용성을 포기함 |
| 5: 기존 기록을 새 키로 재해시 | 원문 ID를 저장하지 않으므로 불가능함 |

## 결과
- 문서: `external_call.request_key` ERD 주석, `consistency-rules.md` (동의 판정·외부 호출 키·호출 예산·일회성 증거), `api-contract.md` (`Device-Check-Token` 헤더), `ssot-deviations.md` 신규, CLAUDE.md 보조 문서 표, ADR-0024·0027·0028·0029 상태 줄.
- 코드 (해당 단계에서): 1 = 단계 5 (접수 행 `consent_version`, `consent` 공개 API·잠금), 4 = 단계 5-1, 5 = 운영 배포 전.
- 사용자 보고: 8의 SSOT 문구 정리. 보고 결과 (2026-11-01): 사용자는 "정책을 SSOT에 맞게"를 지시했다. FR-G-01 31행은 "접수가 허용된 마지막 체험 사진"만 정한 특별 규정이고 FR-E-01은 체험 소진의 일반 규칙이므로, 특별 규정을 따르는 8의 해석이 SSOT와 맞는다. 해석을 유지하고 SSOT는 고치지 않는다.
