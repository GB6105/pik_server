# ADR-0023: 단계 2 공통 기반 세부 결정 (API·오류·멱등·인증·로그)

- 상태: 채택
- 날짜: 2026-10-26
- 관련: 요구사항 `## 트랜잭션과 재시도`·`## 공통 오류와 결과`, FR-A-01·02·03·05, FR-B-01, FR-L-05, ADR-0014, ADR-0016, ADR-0019, ADR-0020, ADR-0021, ADR-0022, 브랜치 `feature/stage2-decisions`

## 맥락
- ADR-0014는 형식 (`ProblemDetail` + `code`, 헤더 API 버전, `Idempotency-Key`, ES256 JWT + refresh 회전, 필드 허용 목록 로그)만 정하고 값과 세부 규칙은 구현 시 확정으로 남겼다. 요구사항도 작업 식별자 형식과 보관 기간을 구현 설계에 맡겼다 (152행).
- 단계 2 (공통 기반 + 익명 주체 발급)를 시작하기 전에 이 값을 정한다.

## 결정
### 사용자 결정
| # | 항목 | 결정 |
|---|---|---|
| 1 | 데이터 버전 위치 | 변경 요청 본문의 대상마다 `version`을 담는다. 응답도 대상별 현재 `version`을 돌려준다. 변경 요청에 `If-Match` 헤더는 쓰지 않는다 |
| 2 | 오류 응답 구조 | RFC 9457 `ProblemDetail`에 `code` (SSOT 분류, HTTP 상태와 1:1), `reason` (세부 사유, 기능별로 추가), `retryable`을 더한다. 장기 작업 응답에는 `jobId`를 담는다. 목록 작업은 200 + `items[]`로 대상별 `result`·`code`·`reason`·`retryable`을 돌려주고, 버전 충돌이면 `currentVersion`도 담는다 |
| 3 | 계정 토큰 수명 | access JWT 15분, refresh 토큰 90일. refresh는 쓸 때마다 교체하고 새 토큰이 다시 90일을 가진다 (마지막 사용부터 90일). 재사용이 감지되면 그 family 전체를 폐기한다. 값은 설정값이다 |
| 4 | 익명 토큰 | 설치 토큰은 발급할 때 기기 증명을 거치고, 만료·교체가 없다. 단말은 Keychain·Keystore에 저장하고 설치 토큰으로 access JWT (계정과 같은 수명)를 받는다. 서버는 설치 토큰을 해시로 저장하고 폐기할 수 있다 |

### 관례적 기본값 (Claude 제안)
| # | 항목 | 결정 |
|---|---|---|
| 5 | 오류 코드 해석 | 서버는 `FORBIDDEN`만 쓴다 (기능 권한·동의·체험·Pro 이용 자격 부재, `reason`으로 구분). `PERMISSION_REQUIRED`는 단말의 OS 권한 결과다 (SSOT "403 또는 단말의 권한 결과"). 다른 주체의 데이터를 요청하면 `NOT_FOUND`로 응답해 존재를 드러내지 않는다. `UNAUTHENTICATED`는 로그인 전용 호출의 세션 부재·만료 (`LOGIN_REQUIRED`)와 함께, access JWT가 없거나 만료된 경우와 설치 토큰이 폐기된 경우에도 쓴다. 설치 토큰 발급 때 기기 증명이 실패하면 `FORBIDDEN` / `ATTESTATION_FAILED` |
| 6 | API 버전 | 요청 헤더 `API-Version`, 첫 값 `1`. 헤더가 없으면 400 (`INVALID_INPUT`). 폐기 예정 버전은 `Deprecation`·`Sunset` 응답 헤더로 알린다. 운영 엔드포인트 (actuator)는 버전 대상이 아니다 |
| 7 | 멱등 기록 | 아래 "멱등 기록 규칙" |
| 8 | JWT | ES256. 클레임 = `iss`, `sub` (주체 ID), `kind` (ACCOUNT / ANONYMOUS), `iat`, `exp`. 헤더 `kid`. 개인정보는 넣지 않는다. 현재 키와 이전 키를 함께 검증해 키를 교체할 수 있게 한다 |
| 9 | 로그 | 필드 허용 목록: trace ID, 주체 ID, 동작, 대상 ID, 상태, 사유 코드, HTTP 상태, 소요 시간. 토큰·`Authorization`·푸시 토큰·이메일·IP와 `data-retention.md`의 금지 항목은 기록하지 않는다 |
| 10 | 기기 증명 | 단계 2는 검증 인터페이스와 개발·테스트용 대역만 만든다. 운영 프로필에서 대역이 켜져 있으면 기동을 실패시킨다. ADR-0020의 "발급할 때 기기 증명"은 운영 배포 전에 실제 App Attest·Play Integrity 검증으로 바꾼다 (STATUS 다음 할 일) |
| 11 | 모듈 골격 | 단계 2는 `shared` (ERD 그룹 '공통 인프라': 오류·멱등·로그·보안)와 `account` (도메인 후보 '계정과 구독' 중 주체·설치·기기·토큰)만 만든다. 구독·이용량의 모듈 경계와 나머지 모듈은 해당 단계에서 정한다 |
| 12 | 공통 응답 필드 (요구사항 172행 해석) | 변경 요청 (Command) 응답은 `jobId`·`result`·`retryable`을 담고, 대상이 여러 개면 `items[]`에 대상별 결과와 `reason`을 담는다. `jobId` = 장기 작업은 서버가 만든 작업 ID, 즉시 처리하는 변경은 요청의 `Idempotency-Key`. `result` = `SUCCEEDED` / `FAILED` / `CANCELLED` / `NEEDS_CHECK` / `ACCEPTED` (장기 작업 접수). 조회 (Query) 응답에는 강제하지 않는다. 최상위 `code`는 HTTP 상태와 1:1이고, `items[].code`는 같은 분류를 HTTP 없이 쓴다. 요청 자체가 잘못되면 4xx, 대상별로 처리했으면 모두 실패해도 200 + `items[]` |
| 13 | refresh 재사용 유예 | 교체 직후 유예 시간 (설정값, 기본 30초) 안에 이전 refresh 토큰이 다시 오면 응답 유실로 보고 family를 폐기하지 않는다. 유예 시간이 지난 재사용은 family 전체를 폐기한다 |

### 멱등 기록 규칙 (결정 7)
- `Idempotency-Key` = UUIDv7, 범위 = (주체, 키), 보관 7일 (설정값). 탈퇴하면 함께 삭제한다.
- 멱등 기록은 업무 변경과 같은 트랜잭션에 저장한다 (ADR-0016·0021). 비정상 종료하면 함께 롤백되므로 처리 중 상태로 남는 기록이 없다.
- 같은 키의 동시 요청은 기록 행 잠금을 기다리고, 잠금 대기 시간 (설정값)을 넘으면 409 `CONFLICT` / `IDEMPOTENCY_IN_PROGRESS` (재시도 가능).
- 결과가 확정된 2xx·4xx 응답은 저장해 같은 응답을 돌려준다. 401, `IDEMPOTENCY_IN_PROGRESS`, 503, 처리 중 예외는 저장하지 않는다.
- 같은 키는 같은 작업의 재전송에만 쓴다. 본문을 바꾸거나 사용자가 다시 시도하는 새 작업은 새 키를 쓴다. 같은 키에 다른 본문 = 400 `INVALID_INPUT` / `IDEMPOTENCY_KEY_REUSED`. 변경 요청에 키가 없으면 400 `INVALID_INPUT` / `IDEMPOTENCY_KEY_REQUIRED`.
- 장기 작업 접수를 재전송하면 저장된 응답 대신 현재 작업 상태를 돌려주고, 만료되는 업로드 URL (S3 presigned)은 다시 발급한다.
- 보관 기간이 지난 재전송은 데이터 버전, `client_ref` 유니크, 사진 버전 유니크 (`analysis_job`·`usage_reservation`)가 중복 반영과 중복 차감을 막는다 (ADR-0021·0022).

## 근거
- 1: 동기화 (FR-L-05)·목록 변경·게스트 귀속 (FR-A-02)은 대상 여러 개에 각자 버전이 필요하다. 헤더로는 대상 하나만 표현할 수 있다. 조회 응답의 ETag (ADR-0019 상태 조회 제안)는 이 결정과 별개다.
- 2: `code`를 SSOT 분류로 고정해 HTTP 매핑을 안정시키고, 기능이 늘면 `reason`만 추가한다.
- 3: 회전과 재사용 탐지가 긴 refresh 기간의 유출 위험을 줄인다. access가 짧아 로그아웃 뒤에 남는 유효 시간이 짧다.
- 4: 익명 주체는 다시 로그인할 수단이 없어, 회전 중 응답이 유실돼 토큰을 잃으면 주체를 복구할 수 없다. 설치 토큰이 유출돼도 피해는 그 설치의 체험 이용량이고, 서버에서 폐기할 수 있다.
- 5: SSOT 오류 표의 "FORBIDDEN 또는 PERMISSION_REQUIRED"를 서버와 단말로 나눠 해석한다. 익명 access JWT를 도입했으므로 `UNAUTHENTICATED`를 "로그인 전용 호출"보다 넓게 쓴다. 두 해석 모두 STATUS 위험 항목에 기록한다.
- 7: 오프라인 단말은 며칠 뒤에 재전송할 수 있다. 업무 변경과 같은 트랜잭션에 저장해야 ADR-0016·0021과 맞고, 비정상 종료 뒤 처리 중 기록이 재시도를 막지 않는다. 503을 저장하지 않아야 일시 장애 뒤의 재시도가 다시 실행된다.
- 12: 요구사항 172행의 네 요소 (작업 ID, 결과 상태, 대상별 사유, 재시도 가능 여부)를 필드에 대응시킨다. 조회에는 작업이 없으므로 강제하지 않는다. 결과 상태 값은 부분 성공 규칙 (성공·실패·취소·확인 필요)을 따른다.
- 13: 회전 응답이 유실된 정상 단말이 family 폐기로 로그아웃되지 않게 한다. 유예가 길수록 탈취한 토큰을 쓸 수 있는 시간이 늘어나므로 짧게 둔다.

| 대안 | 버린 이유 |
|---|---|
| `If-Match` 헤더 | 대상 하나만 표현 |
| 세부 사유까지 `code`에 담기 | `code` 목록과 HTTP 매핑이 기능마다 늘어남 |
| access 1시간 / refresh 30일, access 15분 / refresh 30일 | 사용자 결정 (재로그인 빈도와 유효 시간의 균형) |
| 익명 주체도 refresh 회전 | 토큰 유실 시 익명 주체를 복구할 수 없고, ERD `refresh_token`을 주체 단위로 바꿔야 함 |
| 멱등 보관 24시간 | 오프라인 재전송 기간을 덮지 못함 |
| 멱등 기록을 별도 트랜잭션에 먼저 저장 (처리 중 상태) | ADR-0016·0021과 다르고, 비정상 종료 뒤 남은 처리 중 기록을 정리할 임대 규칙이 필요 |
| refresh 재사용 유예 없음 | 응답 유실만으로 정상 단말이 로그아웃됨 |

## 결과
- `api-contract.md`·`consistency-rules.md`·`data-retention.md`·`domain-boundaries.md`에 세부 규칙을 반영했다.
- ERD: `anonymous_install.revoked_at`을 추가하고, `idempotency_record.status`를 뺐다 (같은 트랜잭션 저장이라 처리 중 상태가 보이지 않음).
- 새 비밀 값: JWT 서명 키 (ES256, `kid`별), 식별자 HMAC 키. 단계 2를 구현할 때 `.env.example`에 키를 추가하고, 로컬은 개발용 키를 `.env.local`에 둔다.
- 구현할 때 Spring Framework 7 API 버전 설정과 Spring Security Resource Server의 키 설정 이름을 공식 문서로 확인한다.
- 계속 미정: 호출 제한 초과 응답 (429 사용 여부, SSOT 오류 표에 없음, D-17), 장기 미사용 익명 설치의 보관 기준 (P08 비로그인 데이터 보관 기한과 함께), `reason` 값 목록 (기능별로 추가).
- 출처: 1~4는 사용자가 정했다 (2026-10-26). 5~11은 Claude가 관례적 기본값으로 시작 보고에 적었고, 사용자는 이견을 내지 않았다. 12·13과 5·7·10·11의 보완은 검토 에이전트의 지적을 받아 Claude가 추가했고, 종료 보고에서 사용자 확인을 받는다.
