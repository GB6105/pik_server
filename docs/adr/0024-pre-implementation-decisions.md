# ADR-0024: 구현 전 미결 결정 일괄 확정 (서버 우선 원칙, 체험·분석·이벤트·구독·알림·검색·장소)

- 상태: 채택
- 날짜: 2026-10-27
- 관련: FR-B-01·03·04·05, FR-I-01·02·06, FR-G-02·03, FR-E-01·03, FR-A-02·04, FR-N-02·03·04, FR-S-01, FR-X-03·05·06, P01, P05, P09, P11, D-10, D-14, D-16, D-17, D-18, D-19, ADR-0016~0023, 브랜치 `feature/pre-impl-decisions`

## 맥락
- 단계 2 이후 각 단계를 구현하려면 결정되지 않은 정책이 테이블 정의, API 입력·응답, 모듈 구조를 막는다.
- 사용자가 "결정하지 않으면 구현할 수 없는 항목"을 막는 단계 순서로 하나씩 정했다. 측정이나 외부 확인이 먼저 필요한 항목 (D-07, D-08, D-09, D-12, D-20, 벡터 모델 합의)과 설정값으로 분리하는 정책 값은 대상에서 뺐다.

## 결정
### 설계 원칙 (사용자 결정)
- **서버에서 해결할 수 있는 판단과 처리는 서버에서 한다.** 단말 구현 (iOS·Android 2벌)을 줄이고, 아직 미정인 정책 값을 서버 설정만으로 조정하기 위해서다.
- 예외: SSOT가 단말 저장을 요구하는 데이터 (비로그인 사용자의 메모·태그·정리 상태·이벤트, FR-A-02), 단말 전용 FR, OS만 알 수 있는 사실 (권한 상태, 사진 변경 신호, 지오펜스 진입).

| 1 | 체험 칸 반환·교체 (P01, 단계 4) | 결과를 만든 체험 칸은 돌아오지 않는다. 사진을 삭제하거나 접근할 수 없게 돼도 반환하지 않고, 체험 대상을 바꾸는 기능도 두지 않는다. 실패·취소 시 예약 반환은 ADR-0021 #3 그대로다 |
| 2 | 비로그인 사용자의 이벤트 판단 (D-16, 단계 5) | 서버가 판단하고 단말이 저장한다. 비로그인 단말이 기존 이벤트 요약 (날짜 범위 안의 이벤트와 제외·숨김·완료 상태)을 보내면, 서버는 판단 결과 (새로 만들기 / 이벤트 X에 붙이기)만 돌려주고 저장하지 않는다. 판단 로직은 기존 이벤트를 입력받는 도메인 서비스 하나로 만든다. 계정 사용자는 DB에서, 비로그인 사용자는 요청에서 기존 이벤트를 받는다. 판단 API는 서버 상태를 바꾸지 않는 조회라 멱등 키와 응답 저장이 없고, `event` 모듈의 분석 완료 구독은 비로그인 주체를 건너뛴다† |

| 4-1 | 최종 실패·취소된 사진 버전의 재접수 (D-19, 단계 5) | 새 작업 행을 만들고 이전 행은 그대로 둔다. 중복 판단은 사진 단위로 한다 (6-1에 따라 버전이 바뀌어도 재분석하지 않으므로)†. 사진에 분석 결과 (직접·재사용·이어받음)가 있으면 버전과 관계없이 새 접수에서 빼고 기존 결과를 돌려주며 차감하지 않는다. 진행 중인 작업이나 반환되지 않은 예약이 있으면 (구성 사진 포함) 새 접수에서 빼고 그 작업 ID를 알려 준다. 최종 실패·취소·대상 아님 (`INELIGIBLE`)만 남은 사진은 새 작업 행을 만들고, 이 세 상태로 끝난 작업의 예약은 반환한다. 유니크는 `uk_analysis_job_photo_active` (`owner_id`, `photo_id`) `WHERE status NOT IN (FAILED, CANCELLED, INELIGIBLE)`와 `uk_usage_reservation_photo` (`principal_id`, `photo_id`) `WHERE status <> RELEASED`다. 일시 실패의 자동 재시도는 같은 행에서 시도 횟수만 늘린다 |
| 4-2 | 서버 배치 작업의 접수 귀속 (D-19, 단계 5) | 배치 (Pro 기존 사진, `PRO_BACKLOG`)가 실행될 때 주체별로 `analysis_request` 행을 만든다 (`origin` = `SERVER_BATCH`). `analysis_job.request_id` NOT NULL을 유지한다 |
| 5 | 유사도 벡터 보관 범위 (P05, 단계 5) | 사진이 있는 동안 서버에 보관한다 (사진 버전·모델 ID·모델 버전과 함께). 사진 삭제, 탈퇴, 비로그인 데이터 삭제 때 함께 지운다. 저장 형식 (pgvector / bytea)과 양자화는 단계 5에서 정한다. 비로그인 주체의 벡터는 다른 비로그인 서버 데이터와 같이 P08 기한에 지운다 (FR-A-02). 기한이 지나면 그 사진은 기존 묶음에 넣거나 대표를 다시 고를 수 없다† |
| 6-1 | 사진 수정 시 재분석 (P05) | 재분석하지 않는다. 새 사진 버전만 기록하고 묶음과 분석 결과는 유지한다. 분석 중에 사진 버전이 바뀌어도 결과는 분석한 버전으로 저장한다 (저장 직전 대조는 유지하되, 버전 차이만으로 결과를 버리지 않는다)†. FR-G-03의 "원본 변경 시 연결·표시 재검증"은 재분석과 별개로 처리한다 |
| 6-2 | 체험 사용자의 재분석 차감 (P01·P05) | 재분석이 생기는 경우에는 남은 체험에서 1장 차감하고, 남은 체험이 없으면 기존 결과를 유지한다. 6-1에 따라 지금은 적용되는 경우가 없으므로 예약 유니크는 사진 기준 (`uk_usage_reservation_photo`, 체험·Pro 공통)으로 둔다. 재분석을 도입하면 (D-09 문자 차이 재분석 포함) 완료 작업·소진 예약도 막는 두 사진 단위 유니크 (`uk_analysis_job_photo_active`, `uk_usage_reservation_photo`)를 함께 바꾼다† |
| 6-3 | 대표 사진 삭제 (P05) | 저장된 벡터로 구성 사진 중 새 대표를 고르고, 공통 분석 결과의 기준을 새 대표로 옮긴다. 새 대표의 결과 출처는 `INHERITED` (원래 작업 ID 유지), 구성 사진의 `source_photo_id`는 새 대표로 바꾼다†. 새 대표는 대표의 원본 삭제가 확인될 때 (`photo.original_deleted_at`) 고르고, 옛 대표가 최근 삭제에서 복구되면 구성 사진으로 돌아온다. 결과가 가리키는 `analysis_job` 행은 옛 대표의 메타데이터를 지운 뒤에도 남긴다†. ## 근거
- 원칙: 판단 규칙이 서버 한 곳에 있으면 로그인 여부·기기와 관계없이 결과가 같고, P05처럼 미정인 기준을 앱 배포 없이 조정할 수 있다 (2, 4, 6-3, 7, 10-2, 12, 13).
- 1: 체험 분석 비용 상한 100건을 지키고, "최초 1회 100장"·"초기 한도 숨김"과 맞는다. 삭제 시 반환하면 분석을 받고 지우기를 반복해 체험을 늘릴 수 있다.
- 2: 비로그인 이벤트를 서버에 저장하는 안은 SSOT FR-A-02 ("로그인 계정 본인의 데이터만 서버에 저장")와 충돌한다. 단말이 판단하면 판단 로직을 서버·iOS·Android에 3벌 구현한다.
- 3: FR-G-02 "이벤트 생성과 독립적으로 결과 확정"을 모듈 경계로 보장하고, 외부 연동 (웹 탐색·번역)이 한 모듈에 모인다.
- 4-1: 끝난 작업과 접수를 다시 바꾸지 않으므로 FR-I-06의 접수별 진행량이 바뀌지 않는다. "반환 후 재시도는 새 예약 행"과 같은 방식이다. "접수마다 새 작업"은 SSOT 23행 "같은 사진·버전을 중복 접수하지 않는다"와 충돌해 뺐다.
- 4-2: "모든 작업은 접수에 속한다"를 DB에서 보장하고 진행 조회 경로를 하나로 둔다.
- 5: Claude는 보관하지 않는 안을 추천했으나, 사용자는 언제든 서버에서 다시 묶을 수 있는 쪽을 골랐다. 늦게 도착한 사진, Pro 기존 사진 배치, 대표 재선정 (6-3)을 서버만으로 처리할 수 있다.
- 6-1: 비용 검토 결과 분석 1건은 약 1원 (Haiku 5.5, 축소 이미지 기준 추정)이지만, 재분석은 액션 생성·웹 탐색까지 다시 실행하고 사용자 이용량을 차감한다. iOS 영구 변경 기록 (`PHPersistentObjectChangeDetails`)과 Android `GENERATION_MODIFIED`는 내용 변경과 메타데이터 변경을 구분하지 않는다. 사용자는 벡터 비교안 대신 재분석하지 않는 쪽을 골랐다.
- 8: 이 기능은 틀린 링크를 확정하는 쪽이 링크가 없는 쪽보다 나쁘다. 추정 비용은 Sonnet 약 100원, Haiku 약 35원 / 1회 (검색 2회 + 페이지 1회 가정, 검색 요금 $10 / 1,000회).
- 9-2: "원래 계정 유지"는 iOS에서 계정 A로 구독했다 해지한 사용자가 계정 B로 새로 구독해도 A에 귀속돼, 결제하고도 권한을 받지 못한다 (RevenueCat 문서). Claude는 활성 구독이 없을 때만 이전하는 안을 추천했으나, 사용자는 기본값 (항상 이전)을 골랐다.
- 9-3: SSOT 문구를 그대로 따르고, 유료 사용자를 잘못 제한하지 않는다. 장애가 길어져도 비용은 Pro 처리량 한도로 묶인다.
- 11-1: Claude는 원인별 처리 (OS 삭제는 유지)를 추천했으나, 사용자는 항상 숨김을 골랐다.
- 12-1: Claude는 정리 독려를 마지막 사용 기기로 보내는 안을 추천했으나, 사용자는 모든 기기를 골랐다. 정리 독려의 판단 기준은 처음에 Claude가 "계정 단위 가장 최근 보고값"으로 보완했다. 검토에서 기기마다 남은 대상이 달라 (iCloud가 아닌 사진, 기기 앨범) 대상이 남은 기기를 놓칠 수 있다는 지적이 나와, 사용자가 기기별 판단을 골랐다.
- 13-1: 비용을 막는 제한이라 일일 한도가 배포·재시작 때 초기화되면 안 된다. UPSERT 비용은 Jev 호출에 비해 작다.
- 13-2: 503은 서버 장애처럼 보여 단말이 바로 다시 시도할 수 있다.
- 13-3: 사진·화면 속 주소를 지도로 연결하는 기능 (iOS 라이브 텍스트, Android Smart Linkify)은 검색어를 지도 앱에 넘기고 장소 확정은 지도 앱에 맡긴다. 외부 API 비용·약관 위험·동의 범위 확대가 없다.
- 13-5: 지오펜스에는 좌표를 미리 저장해야 한다. 카카오 로컬 API는 결과 저장을 금지하고 ("실시간으로 호출하여 사용하는 것만 가능"), API를 활용한 기능에 별도 과금하는 상업적 이용도 금지한다 (카카오 데브톡 FAQ). Google Places는 `place_id` 저장과 좌표 30일 캐시를 허용한다 (Google Maps Platform Service Specific Terms, 2025).

## 결과
- ER 변경 (같은 브랜치): `analysis_request.origin`, 사진 단위 부분 유니크 (`uk_analysis_job_photo_active`, `uk_usage_reservation_photo`가 체험 유니크를 통합), `analysis_job.cause`에서 `MODIFIED` 제거, `analysis_result.source`에 `INHERITED`, `photo_vector` 추가, `trial_click` 대상별 유니크·`usage_quota.guided_at`, `notification_delivery` 추가 (발송 상태·재시도 열을 `notification_schedule`에서 옮김, 예약은 `DISPATCHED`까지만), `event`의 Google 장소 열 (`place_ref`, `place_status`, 좌표, 좌표 보관 기한, 갱신 인덱스), `api_rate_counter` 추가 (API별), `revenuecat_event.app_user_id` NULL 허용 (TRANSFER), `external_call.subject_type`에 `EVENT`, `organize_state.source_album_ref` 의미, `photo_action`의 지도 실행 데이터.
- SSOT 차이:
  - 13-2: SSOT 오류 표에 호출 제한 코드가 없다. `RATE_LIMITED` (429)를 `api-contract.md`에 추가했다. SSOT 수정 여부는 사용자가 정한다.
  - 12-3: FR-N-04 "발송 시 여전히 미허용인지 확인"을 마지막 보고값으로 대신한다 (ADR-0019에서 이어짐).
  - 9-3: FR-B-05 "확인된 만료에만 제한"과 FR-B-04 예외 "일시 장애는 권한을 임의 확대하지 않는다"가 상충한다. 확인 전까지 Pro를 유지하는 것을 권한 확대가 아니라 기존 권한 유지로 해석하고 FR-B-05를 따른다. ADR-0018은 같은 경우를 권한 확대로 봤다.
  - 13-3: FR-X-03 "장소가 모호하면 후보를 선택받는다", "선택한 목적지를 지도에 전달한다"를 지도 앱의 검색 결과에서 고르는 것으로 대신한다.
  - 4-1·6-1: FR-G-01 "같은 사진·버전을 중복 접수하지 않는다" (SSOT 23행)와 FR-I-01 "같은 사진 버전의 중복 분석 여부"를 사진 단위로 넓히고, FR-I-03의 저장 직전 사진 버전 대조에서 버전 차이만으로는 결과를 버리지 않는다.
