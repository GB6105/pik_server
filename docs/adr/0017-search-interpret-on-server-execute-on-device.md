# ADR-0017: 검색 구조: 자연어 해석은 서버, 실행은 단말

- 상태: 채택
- 날짜: 2026-10-25
- 관련: FR-S-01~05, FR-B-05, P02, P10, ADR-0005, ADR-0016, D-02, D-08, D-11, D-14, 브랜치 `feature/tech-stack-design`

## 맥락
- 검색 실행 위치가 정해지지 않았다 (D-02).
- 비로그인 사용자의 메타데이터는 단말에만 있다. 앨범(폴더) 구성과 사진 접근 권한은 OS 기준이라 단말만 안다. Pro는 로그인이 필수다.
- 사용자가 정의한 검색 모델:
  - 자연어 검색은 Basic·Pro 모두 지원한다. Basic = Jev, Pro = Jev + LLM
  - 앨범(폴더)·태그 같은 속성은 사용자가 직접 추가하고, 속성이 있으면 그 범위 안에서 검색한다
  - 속성 뒤의 입력은 자연어로 받는다. 속성만으로도 검색할 수 있다
  - 속성만 있는 검색은 서버를 거치지 않고 단말에서 처리한다
  - 자연어 처리는 전부 서버에서 한다
- Jev (TypeSafe AI)는 텍스트를 생성하지 않는 의사결정 모델이다. 정해진 질문에 선택지·점수·예/아니오 확률을 신뢰도와 함께 돌려준다. 클라우드 API로만 제공된다 (docs.typesafe.ai/api, 2026-10-25 확인: 질문 유형 `noul`·`choice` (선택지 최대 255개)·`score`·`box`).
- Jev 역할 (사용자 정의): 검색어의 의미로 어느 앨범 폴더가 관련 있는지 판단해 가중치를 준다. 예: "2020년에 입었던 파란색 니트" → 여행·옷 폴더에 가중치. 이후 검색은 단말 내부 로직을 따른다.

## 결정
- 서버는 자연어를 검색 계획으로 해석만 하고, 검색 실행은 단말이 한다.
- 흐름:
  1. 단말: 속성 칩은 단말에 두고, 자연어와 폴더 목록 (순번 `ref` + 이름)만 `POST /search/interpret`로 보낸다. `ref`는 OS 앨범 ID가 아니다
  2. 서버: 외부 전송 동의와 이용 자격을 확인한 뒤, 폴더마다 Jev `noul` 질문 ("이 검색어로 찾는 사진이 이 폴더에 있을 확률")을 보내 폴더 가중치를 얻는다. 날짜 표현은 서버의 규칙 기반 해석기가 처리하고, 상대 표현은 `LAST_YEAR_SUMMER` 같은 상대 토큰으로 돌려준다. Pro는 LLM (제안: Haiku 5.5)으로 속성 추출·동의어 확장을 Jev와 동시에 수행한다
  3. 서버 응답 = 검색 계획 (`planVersion`, 폴더 가중치, 날짜, Pro 속성, 적용 조건, 해석하지 못한 부분)
  4. 단말: (속성 범위) AND (검색 계획)을 로컬 인덱스에서 실행한다. 상대 날짜는 단말의 시각·시간대로 변환한다
- 속성만 있는 검색은 1~3단계 없이 단말에서 실행한다.
- 등급 확인: 서버가 이용 자격을 확인하고, Pro 자격이 없으면 Basic 해석으로 응답한다.
- 캐시: Jev 결과를 (정규화한 검색어의 해시, 정규화한 폴더 이름) 쌍 단위로 인스턴스 메모리 (Caffeine)에만 캐시하고 DB에는 저장하지 않는다. TTL은 P08 설정값이다.
- 실패 처리: Jev·Haiku가 타임아웃되면 단말은 검색어 키워드와 날짜만으로 검색하고 "해석 실패"를 구분해 표시한다.
- 남용 방지: 비로그인을 포함해 주체별 호출 횟수를 제한한다.
- 검색 계획 스키마에 버전을 붙이고, 서버가 단말 구현용 적합성 테스트 세트 (계획 + 데이터 → 기대 결과)를 제공한다.
- 구현 세부 (폴더별 `noul` 질문, 상대 날짜 토큰, 캐시 단위)는 제안이다 (D-14).

## 근거
- 해석·실행 분리: 비로그인 검색 (FR-S-01)과 서버의 앨범 비소유 원칙 (ADR-0005)을 함께 지킨다. 사진 ID 목록과 속성 값을 서버로 보내지 않아 요청이 작고 노출이 적다. 서버 검색 인덱스가 필요 없다.
- 폴더별 `noul` 질문: `choice`는 하나만 고르고 확률 합이 1이라 관련 폴더가 여러 개면 가중치가 나뉘며, 선택지가 최대 255개다. `noul`은 폴더별 독립 확률이라 폴더 수 제한이 없고 쌍 단위 캐시가 가능하다.
- 상대 날짜 토큰: 검색 계획이 사용자·날짜와 무관해져 캐시 적중률이 높고 시간대 오류가 없다.
- 만료 처리: 서버가 Pro 해석만 거부하면 Basic 검색이 유지되어 FR-S-02·FR-B-05를 충족한다.

| 대안 | 버린 이유 |
|---|---|
| 모두 서버에서 실행 | 비로그인 메타데이터를 서버에 올려야 해 요구사항과 충돌. 서버는 앨범 구성을 알 수 없음 |
| 자연어까지 모두 단말에서 처리 | 사용자 결정 (자연어 처리는 서버) |
| 서버 실행 + 단말 후처리 필터 | 좁은 속성 범위에서는 상위 K개 결과가 모두 걸러질 수 있음. 서버 인덱스 운영 필요 |
| Jev `choice` 질문 하나 | 관련 폴더가 여러 개면 가중치가 나뉘고, 255개 제한이 있음 |

## 결과
- 자연어 검색은 네트워크가 필요하다. 속성만 있는 검색은 오프라인에서도 동작한다.
- 단말에는 로컬 검색 인덱스 (SQLite FTS5 등)와 검색 계획 실행기가 iOS·Android 각각 필요하다.
- 무료 100장 범위 제한 (P02 가정)은 단말이 적용한다. 앱을 변조하면 우회할 수 있지만 서버 비용에는 영향이 없다. 수용 여부는 P02를 확정할 때 함께 판단한다.
- **SSOT 해석:** FR-S-01의 "메타데이터·Jev 기초 분류로 조회"와 시나리오 S-01의 "Jev 기반 기초 분류 정보"를, 사용자 정의에 따라 "검색어를 Jev로 폴더 관련도에 분류하고 메타데이터로 조회한다"로 해석한다. 사진 단위 Jev 분류는 하지 않는다. `docs/spec`는 수정하지 않았다.
- 앨범 이름은 해석 요청의 입력으로만 쓴다. 앨범 구성 (어떤 사진이 어느 앨범에 있는지)은 서버로 보내거나 저장하지 않으므로 ADR-0005와 충돌하지 않는다.
- 외부 전송에 동의하지 않은 사용자는 자연어 검색을 쓸 수 없고 속성 검색만 쓴다 (ADR-0016, 제안).
- Spotlight (FR-S-05)는 단말 기능이며 이 구조와 무관하다.
- Pro의 의미 기반 순위가 부족하면, 단말이 좁힌 후보 ID를 서버가 재정렬하는 2단계를 측정한 뒤 검토한다.
- Jev 이용 경로·데이터 보관·처리 국가 확인은 D-08, 응답 시간 목표는 D-11에서 정한다.
- 출처: '사용자 결정'으로 적은 항목만 사용자가 직접 정했다. 그 밖의 구성은 Claude 설계안이며, 사용자는 이 ADR의 작성 계획을 승인했고 (2026-10-25), 구성 세부는 종료 보고에서 사용자 확인을 받는다. `(제안)` 항목은 정책 판단이나 SSOT 해석이 걸려 있어, 해당 구현을 시작하기 전에 사용자 확인을 받는다 (D-14).
