# ADR-0022: 스키마 공통 규칙·분석 접수 단위·기기 간 사진 식별 범위

- 상태: 채택
- 날짜: 2026-10-26
- 관련: FR-A-02, FR-A-04, FR-I-01, FR-I-06, FR-L-01, FR-L-05, FR-L-06, P07, P11, ADR-0014, ADR-0016, ADR-0020, ADR-0021, D-15, `docs/erd/pik.erd.json`, 브랜치 `feature/erd-alignment`

## 맥락
- ER 설계안 (`feature/erd-draft`)은 ADR-0021보다 먼저 그려졌다. 첫 Flyway 마이그레이션 전에 ADR-0020·0021과의 정합성을 확인하고 스키마 공통 판단 (D-15)을 확정해야 했다.
- 대조 중 구조 차이 두 가지를 발견했다.
  - ADR-0021 접수 흐름은 사진 여러 장을 받아 작업 ID 하나를 돌려주는데, ER의 `analysis_job`은 사진 1장 단위라 그 작업 ID를 담을 행이 없다.
  - 원본 상태가 사진 단위 값 하나라서, 요구사항 1179행이 구분하라는 권한 철회·다운로드 불가·기기 미보유를 기기별로 표현할 수 없다.

## 결정
### 1. 스키마 공통 판단 (D-15, 사용자 결정)
| # | 항목 | 결정 |
|---|---|---|
| 1 | 소유 주체 | `principal` 하나로 계정 (ACCOUNT)과 비로그인 설치 (ANONYMOUS)를 표현한다. 모든 소유 테이블의 `owner_id`는 `principal.id`다. 탈퇴 후에도 개인정보 없는 최소 행으로 남는다 |
| 2 | 단말 생성 ID | `photo`·`tag`·`event`는 서버 PK (`id`, UUIDv7)와 단말 ID (`client_ref`)를 분리하고 UNIQUE(`owner_id`, `client_ref`)를 둔다. API의 `photoId` = `photo.client_ref`, 다른 테이블의 `photo_id` 열 = `photo.id` |
| 3 | 모듈 간 참조 | 같은 모듈 안에만 FK를 걸고, 모듈 간에는 ID만 저장한다 |
| 4 | 변경 순번 | `owner_change_counter` 행을 같은 트랜잭션에서 갱신해 `change_seq`를 발급한다 |
| 5 | 삭제 | 동기화 대상 root는 `deleted_at` tombstone으로, 이벤트 사진 제외는 `EXCLUDED` 상태로 남긴다 |
| 6 | 분석 결과 | 사진당 현재 결과 1건만 보관하고 이력 테이블을 두지 않는다 |

### 2. 분석 접수 단위 (사용자 결정)
- `analysis_request` (접수 1건)를 추가한다. `POST /analysis-jobs` 응답의 작업 ID는 `analysis_request.id`다.
- `analysis_job`은 대표 사진 1장의 분석 호출 단위가 되고 `request_id`를 가진다. 구성 사진은 묶음을 통해 결과를 이어받고 (REUSED), 구성 사진의 이용량 예약은 대표 사진의 작업을 가리킨다.
- 대상 사진 수와 대표 분석 수는 접수할 때 `analysis_request`에 저장하고, 완료 수는 `analysis_job`을 집계해 계산한다.
- 이미 작업이 있는 사진 버전을 다시 접수할 때와 서버 배치가 만드는 작업의 접수 귀속은 D-19에서 정한다.

### 3. 기기 간 사진 식별 범위 (사용자 결정, ADR-0021 #1 일부 대체)
- iCloud로 동기화된 사진만 기기가 달라도 같은 사진 (같은 `photoId`)으로 본다. 식별자는 iOS PHCloudIdentifier (`photo.cloud_ref`)다.
- 다른 기기에 따로 저장된 사진은 내용이 같아도 별도 사진으로 본다. 지문 (촬영 시각·픽셀 크기·지각 해시) 매칭은 하지 않는다.
- 같은 기기에 다시 설치하면 OS 로컬 ID가 유지되므로 이전 연결을 복원한다. `device` 행은 설치 단위라 재설치하면 새 행이 생기므로, 이전 설치의 연결을 새 설치로 옮기는 방법은 D-20에서 정한다.
- 두 번째 기기가 iCloud 사진에 오프라인으로 붙인 `photoId`를 같은 `cloud_ref`의 서버 `photoId`로 바꾸는 절차도 D-20에서 정한다.
- 단말 생성 `photoId`, (기기, OS 로컬 ID) 매핑, (주체, `photoId`) 소유 검증은 ADR-0021 #1 그대로다.

### 4. 원본 상태 (3에서 파생)
- 사진 행 하나는 기기 1대의 사진이거나 iCloud 사진 1장이다. 그래서 연결된 기기 하나에서 원본 삭제가 확인되면 `photo`를 '원본 없음' (`ORIGINAL_DELETED`)으로 바꾸고 보관 기한을 시작한다 (ADR-0021 #7).
- 권한 축소·다운로드 불가는 기기별 상태 (`photo_device_link.status = INACCESSIBLE`)로만 기록하고 원본 삭제로 보지 않는다. 연결 행이 없는 기기는 그 사진을 보유하지 않은 것이다 (요구사항 1179행).

## 근거
- 1-1: 계정과 비로그인 주체 모두 서버 데이터 (분석·이용량·동의)를 가지므로 (ADR-0020) 소유 검증 기준을 하나로 둔다.
- 1-2: 게스트 데이터를 계정에 귀속한 뒤에도 익명 주체의 행은 P08 기한까지 남는다. 그래서 같은 `photoId`가 두 주체 아래에 동시에 존재할 수 있다.
- 1-3: Spring Modulith 모듈 경계 (ADR-0014)를 DB에서도 지키고, 모듈별 삭제 순서 제약을 없앤다.
- 1-4: DB 시퀀스는 커밋 순서와 번호 순서가 달라 Pull이 변경을 놓칠 수 있다.
- 1-5: 요구사항 1175행 ("전달 완료까지 tombstone을 유지하고 정해진 기한 후 제거")과 같다.
- 1-6: 보관 데이터를 최소화한다 (data-retention). 재분석은 현재 값을 덮어쓴다.
- 2: FR-I-06은 진행 상태 조회에서 "대표 분석 수·대상 사진 수·이용자에게 표시할 진행량"을 구분하라고 한다. 불변 규칙 "장기 작업 접수 응답 = 작업 ID + 진행 상태"를 작업 ID 하나로 지킨다.
- 3: iCloud 사진은 OS가 기기 간 같은 자산임을 보장하므로 식별이 확실하다. 지문 매칭은 오인식 위험 (시나리오 A-03 "임의 사진에 붙이지 않는다")과 기술 검증 비용이 크다.
- 4: 3에 따라 사진 행마다 원본 저장소가 하나라, 한 기기의 삭제 확인이 곧 원본 삭제다. 다른 기기에 남은 사본은 별도 사진이므로, ADR-0021이 즉시 삭제안을 버린 이유 ("다른 기기에 남은 사진의 정보까지 지울 위험")가 생기지 않는다.

| 대안 | 버린 이유 |
|---|---|
| 서버 PK = 단말 `photoId` | 귀속 후 익명·계정 주체에 같은 `photoId`가 함께 있으면 PK가 충돌 |
| 모듈 간 FK | 모듈 경계가 DB에서 결합되고 삭제 순서 제약이 생김 |
| DB 시퀀스로 `change_seq` 발급 | 커밋 순서와 번호 순서가 달라 Pull 누락 |
| 응답에 사진별 작업 ID 목록 | 진행량을 단말이 모아 계산해야 하고, 작업 ID 하나 규칙과 다름 |
| 지문 매칭으로 기기 간 식별 (ADR-0021 #1 원안) | 사용자 결정. 오인식 위험과 기술 검증 비용 |
| 사진 단위 원본 상태 하나 (ER 초안) | 한 기기의 권한 철회·기기 미보유가 다른 기기 표시에 섞임 (1179행) |
| 모든 연결 기기에서 삭제 확인 후 원본 없음 | 3에 따라 연결 기기가 1대이거나 iCloud 사진 1장이라 불필요. 오래 쓰지 않은 기기를 제외하는 규칙이 추가로 필요 |

## 결과
- SSOT와 차이 (사용자 결정): 요구사항 140·948행 (같은 사진의 다른 기기 ID 매칭)과 FR-A-04·시나리오 A-03 (기기 변경 후 복원)을 iCloud 동기화 사진으로 한정한다. 영향은 두 가지다. 첫째, Android 사용자와 iCloud를 쓰지 않는 iOS 사용자는 기기를 바꾸면 기존 Pik 정보가 새 기기의 사진에 연결되지 않는다. 둘째, 한 계정을 iCloud로 묶이지 않은 기기 여러 대에서 쓰면 (예: iPhone + Android, iCloud 없는 iPhone + iPad) 같은 내용의 사진이 기기마다 별도 사진이 된다. 그래서 메모·태그·이벤트 연결이 기기 사이에 이어지지 않고, 분석과 이용량 차감도 기기마다 따로 일어난다. 같은 기기 재설치는 OS 로컬 ID로 복원할 수 있으며, 방법은 D-20에서 정한다. STATUS 위험 항목에 기록한다.
- 게스트 귀속 (FR-A-02)에서 "같은 사진"도 이 기준으로 판단한다: 같은 `photoId`, 같은 `cloud_ref`, 또는 같은 설치의 같은 OS 로컬 ID (단말이 귀속 요청에 함께 보낸다).
- ER 변경: `analysis_request` 추가, `analysis_job.request_id`, `photo.cloud_ref` (부분 유니크), `photo.availability` = `AVAILABLE` / `ORIGINAL_DELETED`, `photo_device_link`의 기기별 상태 (`INACCESSIBLE`·사유·확인 시각). 같은 브랜치에서 ADR-0021 정합화 수정 (`ai_consent.purpose`, `photo.original_deleted_at`, `usage_reservation.photo_version`)도 반영했다.
- 계속 미정: 재접수·배치 작업의 접수 귀속 (D-19, 단계 5 마이그레이션 전), photoId 수렴·재설치 연결 이관 (D-20, 단계 9 전), PHCloudIdentifier 신뢰성 (FR-A-04 기술 검증), 접수 단위 상태명 (단계 5 구현 시), 유사도 벡터 보관 범위 (ADR-0021).
- 출처: 결정 1·2·3은 사용자가 정했다 (2026-10-26). 결정 4와 게스트 귀속의 같은 사진 판단은 결정 3에서 Claude가 정리했다.
