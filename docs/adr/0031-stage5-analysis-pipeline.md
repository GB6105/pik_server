# ADR-0031: 단계 5 분석 파이프라인 설계 (접수·실행·정산·생성)

- 상태: 채택 (설계 계약, Codex 비판 검토 R1~R8 수렴, 2026-11-01). #11 실행 모드·#12 불명 재호출은 사용자 결정 대기 (D-25·D-26)
- 날짜: 2026-11-01
- 관련: FR-I-01·02·03, FR-G-01~03, FR-E-01, ADR-0016 #5 대체, ADR-0021, ADR-0024 #1·#4-1·#4-2·#6-3, ADR-0029, ADR-0030 #1·#2·#3 보완, 설계 문서 `docs/design/stage5-analysis-pipeline.md`

## 맥락
- 사용자가 단계 5를 "모델과 무관한 계약"으로 착수하고, PR 3개 (5-1 접수 / 5-2 실행 / 5-3 생성)로 나누고, 신규 모듈을 `photo` + `analysis`로 두라고 정했다.
- 사용자가 Codex와 함께 설계를 비판적으로 검토하라고 지시했다. 기준은 안정성·비용·속도다. Claude가 제안하고 Codex가 비판하는 라운드를 8회 진행했고, 마지막 라운드에서 Codex가 이 단위를 "확정 가능"으로 판정했다.
- 세부 계약 (상태표·정산표·DDL·API·성능 기본값)은 설계 문서에 둔다. 이 ADR은 구현 방향을 정하는 결정만 기록한다.

## 결정
| # | 항목 | 결정 |
|---|---|---|
| 1 | 모듈 경계 | `photo` = 서버 사진 행·원본 버전 관측, `analysis` = 접수·작업·시도·호출·결과·예산. `action`·`event`는 각자 생성 행을 소유하고, `usage`는 사진별 정산 API를 더한다. FK는 모듈 안에서만 두고, API의 `photoId` = `photo.client_ref` |
| 2 | 잠금 순서 | 모든 TX는 `멱등 키 → 동의 → 주체 접수 → 주체 이벤트 → 전역 claim → photo → analysis_request → analysis_job → external_call → 이용량 할당 → 주체 일일 송신 → 기기 기록 → photo_ai_budget → 일일 비용 → 생성 행 → photo_action·event → owner_change_counter` 순서로만 잡는다 |
| 3 | 실행 근거 | 자동 실행 값은 공통 전제 (소유·현재 대상·종류별 값 검증)를 통과하고, 사용자가 편집했거나 확인 이후 원본이 바뀌지 않았거나, 근거가 `DIRECT ∧ READ ∧ VALID`이고 결과의 기준 버전이 현재 원본 버전 이상일 때만 실행 가능하다. 그 밖은 `NEEDS_CHECK` |
| 4 | 원본 버전 관측 | `photo.source_change_seq`는 관측값이 바뀔 때만 1 증가하고 `PhotoSourceChanged`를 발행한다. 접수 항목은 사진마다 `basis_change_seq`를 기록한다 |
| 5 | 업로드 | 접수 응답에는 업로드 URL을 넣지 않는다. 시도 발급 API가 작업별 presigned PUT (`If-None-Match: *`, SHA-256 checksum)을 발급하고, 작업당 신규 발급은 5회까지다. 같은 멱등 키의 재생은 저장된 시도의 URL을 같은 만료로 다시 서명한다 |
| 6 | 전송 경계 | 허가 TX (동의·예산·기한·manifest 검사 + `external_call` 삽입)의 커밋이 전송 시작 경계다. HTTP는 1회만 보내고 SDK 재시도는 끈다 |
| 7 | 정산 | 응답별 비용·위험 송신·체험 예약 처리는 설계 문서 2.5 정산표 하나만 따른다. 사용량 없이 최대 비용으로 정산하는 응답은 위험 송신도 소진하고, 401·403·404만 횟수를 해제한다 |
| 8 | 사진별 체험 정산 | 성공 완료 TX는 예약을 결과를 저장한 사진 C와 삭제된 구성원 D로 나눠 `usage.settle(principal, job, C, D)`를 한 번 호출한다 (C = consume, D = release). 기존 작업 전체 consume/release를 순서대로 부르지 않는다. 실패·취소·대상 아님은 전체 반환 |
| 9 | 예산 | 전역 일일 비용 (`ai_spend_day`), 체험 기기 평생 송신 (체험 한도 × 2), 주체 일일 송신 300, 사진 평생 위험 송신 3, 동시 실행 (전역·주체 4), 입력 속도 제한을 둔다. 전역 차단은 원인별 `ai_gate` 행으로 claim 전에 거른다 |
| 10 | 우선순위 | `effective = max(0, 2×base + 1 − floor(대기/10분) − (첫 결과 없음 ? 1 : 0))`, base = 새 사진 0·정리 1·Pro 백로그 2. 동률은 `queued_at, job_id` |
| 11 | 실행 모드 (사용자 결정 대기, D-25) | 제안: 체험 첫 실행도 Messages, Batch는 Pro 최초 처리량만. **결정 전에는 ADR-0016 #6 (대량 백로그 = Message Batches)을 유지**한다 |
| 12 | 불명 응답 (사용자 결정 대기, D-26) | 결과를 알 수 없는 호출은 최대 비용·위험 송신 소진으로 확정한다. 제안: 사진 수명 동안 1회만 자동 재호출 (`photo_ai_budget.unknown_retry_used`, 중복 과금 감수). 값은 설정으로 끌 수 있게 구현한다 |
| 13 | 회로 | 설정 오류 회로 (401·403·404, 400 비율)는 운영자 해제 또는 설정 버전 변경까지 열리고, 해제 뒤 probe 1건으로 확인한다. 일시 회로 (429·529·5xx)는 지수 백오프로 반개방한다 |
| 14 | 호출 manifest | 모델·프롬프트·스키마·thinking·effort·입출력 상한·가격 버전을 묶은 불변 행을 접수 때 작업에 고정한다. 실행 가능한 manifest = 현재 + 이전 |
| 15 | 결과 스키마 v1 | 모델과 무관한 내부 DTO + JSON Schema. 실행 값은 자르지 않고 `INVALID`로 둔다. 전화 자동 근거는 명시 국가 코드·연결 주소만 쓴다 |
| 16 | 생성 리스너 | `@ApplicationModuleListener(propagation = NOT_SUPPORTED)` 조정 리스너가 다른 빈의 TX 메서드로 본체를 실행하고, 본체 TX가 끝난 뒤 실패 기록 TX를 실행한다. 상한 (5) 미만이면 예외를 다시 던지고, 종결되면 정상 반환한다 |
| 17 | 이벤트 판정 | 날짜·시각·장소는 사용자 확정값, 행사명은 자동 근거만 비교한다. 판정 = `LINKED`/`CREATED`/`AMBIGUOUS`/`SUPPRESSED`. 비로그인 요약이 불완전하면 연결·생성을 모두 하지 않는다 |
| 18 | 보관 | `SUCCEEDED` 작업·접수는 그 작업을 가리키는 결과가 있는 동안 유지 (ADR-0024 #6-3). 유니크는 `uk_analysis_job_photo_active WHERE status NOT IN (FAILED, CANCELLED, INELIGIBLE)` (ADR-0024 #4-1). `external_call` 90일 |
| 19 | 활성화 | 접수는 `pik.analysis.intake-enabled` (기본 false)로 켜고 끈다. 세 PR이 모두 병합되고 프로필별 리스너 시험이 통과한 뒤 켠다 |

### 보완하는 기존 결정
- ADR-0016 #5 (결과 불명 = 확인 필요 상태 + 재대조 배치): 재대조할 제공자 계약이 없으므로 #12로 대체한다. 무조건 재호출하지 않는다는 원칙은 유지한다 (사진 수명 1회 상한).
- ADR-0030 #1: 동의 기준 버전 검사를 시도 발급·확정·허가·완료 TX의 공통 조건으로 넣는다.
- ADR-0030 #2: 호출 시도 예산·전역 비용 예산 구조를 #9로 정한다.
- ADR-0030 #3: 결과를 알 수 없는 호출의 종료 규칙을 #12로 정한다.

## 근거
- 1·8: ADR-0024 #1은 결과를 만든 사진만 체험을 소모한다고 정했다. 기존 `TrialUsage.consume/release(principal, job)`는 작업 전체를 처리하므로, 구성원이 처리 중 삭제되면 그 칸까지 소모한다. 사진 단위 정산이 필요하다.
- 6: 외부 호출을 DB 트랜잭션에 포함하지 않는다는 불변 규칙을 지키면서, 복구 때 "보냈을 수 있는 호출"을 DB 행으로 찾을 수 있다.
- 7: 사용량이 없는 응답에서 횟수를 해제하면 같은 사진을 무한히 다시 보낼 수 있다. 401·403·404는 우리 설정 오류이므로 회로가 반복을 막는다.
- 11: Batch는 최대 24시간이 걸려 첫 체험 경험이 늦다. 동기 호출은 사진 1장에 약 $0.00058~0.00081이고 Batch는 그 절반이다 (2026-11-01 추정). 비용과 첫 결과 시간의 교환이므로 사용자가 정한다.
- 12: Anthropic Messages API는 요청 키로 응답을 다시 조회하는 계약이 없다 (ADR-0030 #3). 재호출하면 중복 과금 위험이 있고, 재호출하지 않으면 일부 사진이 결과 없이 끝난다.
- 16: Spring Modulith 2.1.2의 리스너는 정상 반환해야 완료로 기록하고, 예외를 던지면 실패로 기록한다. 본체 TX 안에서 실패를 기록하면 본체 롤백과 함께 사라진다.

| 대안 | 버린 이유 |
|---|---|
| 8: 구성원 삭제 시 전체 consume | ADR-0024 #1 위반 (결과 없는 칸 소모) |
| 12: 불명이면 바로 실패 | 일시 장애마다 사용자가 결과를 잃음. 사용자 결정으로 남김 |
| 15: 단말 기본 국가로 번호 국가 추론 (`UNIQUE_DEFAULT_REGION`) | `02-212-3456`은 26개 지역, `010-2000-0000`은 7개 지역에서 유효해 잘못된 자동 실행 위험 |
| 16: 리스너 20회 실패 필터로 종료 | Modulith JDBC는 LIMIT로 먼저 읽고 필터를 뒤에 적용해 뒤의 정상 대상을 가림 |
| 18: 종료 작업 90일 삭제 | 결과가 가리키는 작업이 사라짐 (ADR-0024 #6-3 위반) |

## 결과
- 단계 5 구현 PR (5-1·5-2·5-3)은 설계 문서를 기준으로 하고, 실제 DDL·API와 다르면 설계 문서를 함께 고친다. ERD 반영은 각 구현 PR에서 한다.
- `usage` 모듈에 `settle(principal, job, C, D)`를 추가하고 예약별 최종 상태로 멱등을 판정한다. 기존 `uk_usage_reservation_photo`는 그대로 둔다.
- D-07 측정이 manifest 값 (effort·해상도·OCR·`max_tokens`)을 정한다. 값은 설정이므로 코드 변경 없이 바뀐다.
- D-25·D-26은 5-2 구현 전에 사용자 결정이 필요하다.
