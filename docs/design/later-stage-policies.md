## C1 RevenueCat 요금제 (D-12) — 해소 제안
- RevenueCat Pro: 월 추적 매출 (MTR, 스토어 수수료·세금 공제 전) $2,500 이하 무료, 넘으면 **전체 MTR의 1%** (예: $2,600 → $26). 웹훅·REST 포함. 별도 계약 불필요 (2026-11-01 확인). 장기 손익에는 1%를 넣는다

## C2 Pro 처리량·가격 (P03 → 사용자 결정)
- 구조: `quota_kind` = `PRO_INITIAL` / `PRO_DAILY` (KST 0시)
- `PRO_INITIAL` = **계정당 1회 ∧ 지급 근거 (최초 구매 건) 재사용 금지** (grant 원장). REST의 Pro=true만으로 지급하지 않음, 근거 확인 전에는 권한 활성 + 지급 대기
  - 재구독·복원 = 재지급 없음. TRANSFER = 권한만 이동, 수신 계정 신규 지급 없음, 원 계정 잔량은 원 계정에 남고 Pro가 없으면 사용 불가
  - 탈퇴 뒤 같은 구매로 새 계정 = 사용자 결정 (추천: 첫 출시는 추가 식별자 보존 없이 감수, 1회 남용 비용 ≈ Batch $0.87~1.22). 막으려면 ADR-0020 최소 기록에 새 식별자 추가 승인 필요
  - 결제 식별 키·RevenueCat 조회 필드의 충분성은 단계 8에서 확인
- 초기량은 지급 자격이지 당일 송신량이 아니다. 단계 8 backlog는 주체 일일 송신 한도 (300)·처리 기한 (48시간) 안에서 나눠 접수하고 새 사진을 우선
- 장당 비용 (단계 5 설계 문서, 사진마다 호출, Messages): $0.00058~0.00081. Batch 절반
- 손익 (분석비만, 스토어 15%/30% 가정, RC 1% 포함, 일 100장 × 30일 = $1.74~2.43/월, 초기 3,000장 Batch = $0.87~1.22):
  | 월 가격 | 스토어 | 수취액 | 월 분석비 뒤 | 첫 달 (초기 Batch 포함) | 안전계수 0.5 일 한도 |
  |---|---|---|---|---|---|
  | $3 | 15% / 30% | $2.52 / $2.07 | $0.09~0.78 / −$0.36~0.33 | −$1.13~−0.09 / −$1.58~−0.54 | 51 / 42장 |
  | $5 | 15% / 30% | $4.20 / $3.45 | $1.77~2.46 / $1.02~1.71 | $0.56~1.59 / −$0.20~0.84 | 86 / 70장 |
  | $8 | 15% / 30% | $6.72 / $5.52 | $4.29~4.98 / $3.09~3.78 | $3.08~4.11 / $1.88~2.91 | 138 / 113장 |
- 일 100장을 유지하려면 가격 약 $5.79 (15%) / $7.05 (30%) 이상 (안전계수 0.5 기준, 다른 원가 제외)
- 만료 전 접수·예약한 작업 = 완료까지 처리·차감, **확인된 만료** 뒤 새 접수 거절 (FR-I-01, FR-B-05, ADR-0024 #9-3: RevenueCat 장애로 확인 못 하면 Pro 유지)

## C3 분석 측정 (D-07) — 절차
- 모델 = Haiku 5.5 고정. 불합격이면 입력·프롬프트·스키마·검증·확인 UX를 먼저 조정. 다른 모델 상향은 측정 근거를 붙여 별도 사용자 확인
- 실험: thinking 정책 먼저 고정 → effort (`low`/`medium`) × 해상도 (1092/1568px) × OCR 동봉 (C4) = 8조합, 2,400회, 약 $1.4~1.9 (라벨 비용 제외). 실제 지원 조합은 API로 확인
- 표본: 실제 사진 300장 이상, **탐색·검증 분리** (연속 촬영 세트는 한쪽에만). 해외 번호가 있는 한국어 문서, 시간대·연도 누락, 같은 상호·다른 장소, 작은 글자, 여러 일정, 일반 사진의 무근거 추출 포함
- 각 실행 = 호출 manifest (단계 5 설계 문서 2.5) + 데이터셋·정답 버전
- 지표 (분모 고정): 번호 exact match, 날짜·시간대 정규화 정확도, 자동 `READY` 필드의 잘못된 확정 비율, 정답 recall, 자동 실행 coverage, `NO_RESULT`·`INVALID`·`TRUNCATED` 비율, 이벤트 오병합률·중복률·확인 요청률, 비용 (평균·p95·최대 예약, cache cold/warm), 지연 (제공자 HTTP·업로드 확정 → 생성 완료)
- 합격 기준 (초안): 번호·날짜 정확도 ≥ 95%, 잘못된 `READY` ≤ 1%, 평균 장당 비용 ≤ $0.001, 제공자 HTTP + 서버 처리 p95 ≤ 10초 (오프라인 측정, B3의 E2E 30초와 별개). 전부 `NEEDS_CHECK`로 위험률만 낮추는 설정은 불합격 (coverage 하한 함께)
- 통계: `READY` 검증 표본 수와 coverage 하한을 측정 전에 고정. 분모 = 탐색에 쓰지 않은 평가 단위, 같은 사진의 여러 필드를 독립 건으로 세지 않음. 독립 300건 0 오판의 단측 95% 상한 ≈ 0.99% (`1−0.05^(1/300)`)
- 묶음 θ·W도 같은 절차. 기한 = 5-2 구현과 함께 (설정값만 바뀜)
- 검색 블록 비용 (ADR-0031 #20): 같은 입력으로 "검색 블록 없음 / 있음"의 총 토큰·평균·p95 비용·지연·`TRUNCATED` 비율을 cold/warm 캐시별로 비교. 상한 안에 들지 않으면 항목량을 먼저 줄이고 `max_tokens`·manifest 최대 비용을 다시 계산
- 검색 품질: 실제 검색어 50개 이상 (무정답 질의 포함) × 정답 사진 집합, 탐색·검증 분리 (연속 촬영 세트는 한쪽에만). 지표 = recall@20, nDCG@20, 무정답 질의 오검출률. 평가 단위 (묶음 접기 전/후)·Basic/Pro 지원 조건·합격 기준을 측정 전에 고정. 관계 반례 ("빨간 니트 앞 파란 벽"), 미상·상속·미분석 표본 포함
- 개인정보 거절 표본: 금지 속성을 유도하는 사진에서 출력 0건 확인 (표본 0건 ≠ 운영 무누출 보장)

## C5 Jev 이용 조건 (D-08)
- early access 신청 + 데이터 보관·학습 사용·처리 국가 서면 확인. 기한 = 운영 동의 문구·제공자 목록 확정 전 (단계 11 착수 전보다 앞섬)

## C6 검색 캐시 (D-14 검색 항목)
- 폴더별 관련도 Caffeine 캐시 (인스턴스 메모리, 크기 상한), 키 = (주체, 정규화 질의, 폴더 이름, 모델·규칙 버전). 상대 날짜는 상대 토큰으로 반환하므로 날짜 키 불필요. Pro 추가 해석과 분리. 권한은 캐시 적중 때도 검사. DB·Redis 없음

## C7 iCloud 사진 수렴 (D-20) — 검증 계획 + 출시 의존성
- FR-A-04 실기기 검증: 제한 사진 접근·동기화 지연·삭제 후 복원·오프라인 재접속 포함
- 규칙 초안: 같은 (주체, `cloud_ref`) 사진 둘 = 먼저 만든 서버 사진이 정본. **alias 먼저 기록** (새 접수를 정본으로) → 진행 작업 종료는 TX 밖에서 기다림 → 짧은 병합 TX에서 두 사진 ID를 정해진 순서로 잠가 최신 상태 재검사 후 멱등 병합. `cloud_ref` 일치는 식별 힌트일 뿐 소유 검증을 대신하지 않음
- 병합: 사용자 편집·숨김·확인 보존, 액션·이벤트 출처 갱신, tombstone·`change_seq`, `risk_sends` 합산, `unknown_retry_used` OR, `source_change_seq`는 MAX로 합치지 않고 자동 확인은 다시 받음. 소비한 체험·비용은 되돌리지 않음
- 계정 다기기 분석 출시는 D-20 뒤. 기한 = 단계 9 전

## C9 알림·길이·검색 범위 (P09·P10·P02 → 미정 정책)
- P09: 정리 알림 1·2·3·5·7·14일 초안. 정리 독려의 대상·시점·단계는 기존대로 **기기별** (ADR-0024 #12-1). 서버의 주체별 묶음·일 발송 상한 (숫자는 사용자 결정)·정리/숨김/권한 철회 시 소거·다기기 중복 억제는 발송 제한일 뿐 (단계 9 설계)
- P10: 메모 2,000자, 태그 30자, 사진당 태그 20개, 검색 페이지 50개 초안. 길이 기준 = 사용자 인식 글자 (grapheme), 정규화 (NFC) 뒤 검사 + 필드·본문별 UTF-8 바이트 상한 (결합 문자 반복 방어)
- P02: 무료 기초 검색 범위 = 체험 100장 초안. 추천 = 무료는 체험 결과, Pro 만료자는 이미 생성된 결과의 Basic 검색 유지 (새 유료 분석·Pro 해석 자격과 저장 결과 사용을 분리). 사용자 결정

## C10 검색 색인 동기화·검색 계획 계약 (단계 9·11, ADR-0031 #20)
- 단계 9 동기화: 신규·기한 경과 클라이언트의 현재 상태 전체 동기화 → 증분 전환 기준점. cursor는 주체·피드·복구 세대에 묶음, 409면 단말의 서버 파생 색인을 교체 재구축. 계정 복원과 익명 재설치 (새 주체) 구분. 분석 결과 변경 (검색 투영·`searchTimePlace` 포함)을 같은 경로로 전달
- 묶음·대표·구성 버전과 변경을 동기화에 포함 (대표 교체는 새 결과 없이도 일어남). 표시·수는 단말 접근 상태로 다시 계산. 상속된 같은 텍스트가 상위 결과를 독점하지 않게 묶음 표시 규칙을 적합성 시험에 포함
- 사용자 정보 버전·OS 접근 상태 변경을 색인에 별도 반영. 일괄 작업은 성공 사진만 갱신. 재색인은 이미지 재분석·재과금을 일으키지 않음
- 검색 가능 범위 (FR-S-02): 서버가 계산한 "분석 완료·검색 가능 범위"와 미분석·실패·폐기·빈 결과 구분을 반환 (모델 출력으로 받지 않음)
- 단계 11 검색 계획 계약: 계획의 조건·동의어·AND/OR가 어느 색인 필드에 적용되는지 버전 계약 + iOS/Android 공통 적합성 예제. 지원하지 않는 관계는 미해석. Basic에서 분석 결과를 쓰는 방식은 확정된 Basic/Pro 범위 (ADR-0017) 안에서 정하고 이 설계로 넓히지 않음. P02는 사용자 결정 대기 유지
