## 막힌 점·이슈
- `TestcontainersConfiguration`이 package-private이라 하위 패키지 테스트가 쓸 수 없었다. public으로 바꿨다.
- 코드 검토에서 DispatcherServlet 밖의 오류 (필터 예외, `sendError`)가 `code` 없는 Boot 기본 오류 응답으로 나가는 문제가 나왔다. `/error` 컨트롤러로 같은 형식을 쓰게 했다.
- 재검토에서 Tomcat이 필터의 `ServletException` 메시지를 `message`에 남기는 것이 확인됐다. 해당 로거를 끄고 테스트로 감시한다.
- 라이브러리 예외 메시지가 `stack_trace`로 로그에 남을 수 있어, 예외 클래스 이름만 남기는 printer를 등록했다.
- 2-2: Spring의 HibernateJpaDialect가 JpaTransactionManager에 savepoint를 제공하지 않아 (`NestedTransactionNotSupportedException`), 트랜잭션에 묶인 JDBC 연결에서 savepoint를 만들었다. 이 방식은 코드 검토에서 폐기했다 (다음 항목).
- 2-2 코드 검토: savepoint로 되돌려도 rollback-only 표시와 트랜잭션 후속 처리 (이벤트 리스너)가 남았다. `@Transactional` 참여 메서드가 4xx를 던지면 503이 반복되고, 거부된 요청의 이벤트 리스너가 실행됐다. 검토 에이전트의 탐침 테스트로 재현했고, 4xx면 트랜잭션 전체를 롤백한 뒤 새 트랜잭션에 기록하도록 바꿨다 (ADR-0026 #2, 사용자 확인).
- 2-2: PostgreSQL 잠금 대기 초과 (SQLSTATE `55P03`)를 Spring이 분류하지 않아 (`UncategorizedSQLException`) SQLSTATE로 직접 판별했다. 동시성 테스트가 잡아냈다.
- 요구사항 오류 표에 500이 없어, 예상하지 못한 예외를 503 `TEMPORARY_FAILURE`로 대응했다. 405도 대응 코드가 없어 422 `UNSUPPORTED_OPERATION`으로 바꿨다 (ADR-0025).

## 회고 메모
- 잘된 점: 구현 전에 Boot 4.1.2의 설정 이름과 API를 공식 소스로 확인해, 첫 실행에서 테스트가 모두 통과했다.
- 문제: 첫 구현은 MockMvc로만 검증해, 실제 서버에서만 지나가는 오류 경로 (필터 → `/error`)를 놓쳤다.
- 교훈: 로그 허용 목록은 실제 출력 한 줄을 확인해야 의도대로 걸러지는지 알 수 있다. 오류 응답은 RANDOM_PORT 서버로 필터 밖 경로까지 확인한다.
- 교훈 (2-2): 트랜잭션 일부만 되돌리는 방식은 DB 변경 밖의 상태 (rollback-only 표시, 후속 처리 등록)까지 되돌리는지 확인해야 한다. 테스트가 JDBC 변경 한 가지만 봐서 놓쳤다.
