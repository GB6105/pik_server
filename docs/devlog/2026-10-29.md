## 막힌 점·이슈
- 공개 경로 matcher를 Boot 빌더로 바꾸면서 파라미터 이름이 지역 변수와 겹쳐 컴파일이 실패했다. 이름을 바꿔 다시 빌드했다.
- 첫 재검토에서 살아남은 변이 1개 (`sendError` 대체 경로 삭제)는 실행하는 테스트가 없어서였다. 렌더링이 실패하는 처리기로 단위 테스트를 추가했다.
- 단계 3 진행 중 사용자가 검색이 동작하지 않는 이유를 물었다. 검색 해석 (FR-S-01~04)은 단계 11이고 D-08·D-14가 선행이라 아직 서버에 없다고 답했고, 사용자는 단계 3을 계속하기로 했다.
- 병렬 동의 요청만으로는 UNIQUE 위반 경로가 실행되는지 보장되지 않아, 오래된 조회를 흉내 내는 테스트로 실제 DB의 위반 경로를 직접 확인했다.
- 검토에서 "같은 결정 반복은 기록 안 함" 규칙 때문에 순번이 오르지 않아, 늦게 도착한 동의가 그 뒤 거절을 덮는 경우가 재현됐다. 모든 결정이 순번을 올리도록 바꿨다.
- Hibernate는 PostgreSQL 제약 이름을 오류 메시지 문구에서 꺼내므로, 서버 메시지 언어가 영어가 아니면 이름이 없다. 판별을 SQLState 기반 제약 종류로 바꿨다.
- 시작 보고에서 DeviceCheck 비트를 "커밋 뒤 outbox로 갱신"하겠다고 했으나, 비트를 바꾸려면 토큰이 필요하고 토큰 원문은 저장할 수 없었다 (`data-retention.md`). Apple 문서는 토큰 유효 기간을 밝히지 않는다. 사용자에게 다시 물어 첫 체험 접수 때 단말이 보낸 새 토큰으로 기록하기로 했다 (ADR-0029 #5-1).
- 검토에서 iOS 설치를 시작 전에 여러 번 등록하면 설치마다 체험을 받는 경우가 나왔다. 기기 기록이 설치마다 새로 생기는데, 시작 기록 때 비트를 조회하지 않고 쓰기만 했기 때문이다. 쓰기 전에 조회하고, 쓰기 결과를 확인하지 못한 기록은 `STARTING`으로 남겨 재시도가 조회 없이 다시 쓰게 했다 (#18).
- HMAC은 블록 크기보다 짧은 키를 0으로 채우므로, 0으로 채운 32바이트 키와 40바이트 키가 같은 해시를 냈다. 키 순서 테스트가 이 때문에 실패해 다른 값으로 채운 키를 썼다.

## 회고 메모
- 교훈 (단계 3): 낙관적 순번은 받아들인 요청마다 올라야 한다. "변화 없음"을 기록하지 않는 최적화는 같은 순번으로 보낸 늦은 요청을 통과시킨다.
- 교훈 (2-3): 엔티티의 `@Version`은 단말이 바꾸지 않는 활동 시각까지 충돌 대상으로 만든다. 자주 갱신되는 시각은 조건부 UPDATE로 분리한다.
- 교훈 (2-3): 공개 경로도 `Authorization` 헤더가 있으면 인증 필터가 먼저 검사한다. 토큰을 새로 받는 경로는 헤더를 무시해야 한다.
- 교훈 (단계 4): 외부 상태를 나중에 바꾸는 설계는 그때 필요한 자격 증명을 다시 얻을 수 있는지부터 확인한다. 저장 금지 값이 필요하면 단말이 그 시점에 다시 보내야 한다.
- 교훈 (단계 4): 외부 기록이 "한 번만"을 보장해야 하면 쓰기 전에 읽고, 쓰기 결과를 모르는 상태를 따로 둔다. 쓰기만 하면 같은 기기의 다른 설치를 구별하지 못하고, 모르는 상태를 실패로 되돌리면 이미 쓴 기록을 다시 조회해 체험을 잃는다.
