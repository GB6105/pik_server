# 트랜잭션·재시도·멱등성

근거: 요구사항 `## 트랜잭션과 재시도`.

## 트랜잭션
- 한 DB 트랜잭션 = 같은 저장소에서 함께 확정할 상태만
- 외부 시스템(AI·플랫폼 결제·OS)은 트랜잭션 밖

## 외부 작업 4단계
1. 실행 의도 저장
2. 외부 호출
3. 실제 결과 확인
4. 결과 기록

- 중단 시 결과 재대조. 미확인 결과 = `확인 필요` 상태 유지
- 서버 저장과 후속 요청이 분리돼 유실 가능 → 실행 의도를 함께 기록 후 재처리
- outbox = Spring Modulith event publication registry (JDBC), 작업 큐 = 업무 테이블 + `SKIP LOCKED` (ADR-0014)

## 멱등성
- 변경 요청 = 작업 식별자 + 데이터 버전
- 같은 작업 재전송 → 수행 단계와 대조, 중복 과금·삭제·등록 금지
- 같은 사진 변경 알림 중복 수신 → 분석·액션·이벤트 중복 생성 금지
- 키 = `Idempotency-Key` (UUIDv7), 범위 = (주체, 키), 보관 7일 (설정값), 탈퇴 시 삭제 (ADR-0023)
- 멱등 기록 = 업무 변경과 같은 트랜잭션에 저장. 비정상 종료 시 함께 롤백 (처리 중 기록 없음)
- 같은 키 동시 요청 = 기록 행 잠금 대기 → 대기 시간 (설정값) 초과 시 409 `CONFLICT`/`IDEMPOTENCY_IN_PROGRESS` (재시도 가능)
- 저장 = 결과가 확정된 2xx·4xx → 같은 응답 반환. 4xx는 업무 변경 롤백 + 멱등 기록만 커밋. 401·`IDEMPOTENCY_IN_PROGRESS`·503·처리 중 예외는 저장 안 함. `IDEMPOTENCY_KEY_REUSED`는 원본 기록 유지
- 200 응답 `items[]`의 재시도 가능한 실패 = 그 대상만 새 키로 재전송
- 같은 키 = 같은 작업의 재전송만. 본문 변경·사용자 재시도 = 새 키. 같은 키·다른 본문 = 400 `INVALID_INPUT`/`IDEMPOTENCY_KEY_REUSED`. 키 누락 = 400 `INVALID_INPUT`/`IDEMPOTENCY_KEY_REQUIRED`
- 장기 작업 접수 재전송 = 저장 응답 대신 현재 작업 상태 + 업로드 URL 재발급. 저장 본문에 업로드 URL 넣지 않음
- 보관 기간 이후 재전송 = 데이터 버전·`client_ref` 유니크·사진 버전 유니크 (`analysis_job`·`usage_reservation`)로 중복 반영·차감 차단 (ADR-0021·0022)

## 부분 성공
- 목록 작업은 항목별 `성공·실패·취소·확인 필요` 반환
- 재시도 대상에서 이미 성공한 항목 제외

## 동기화
- 로컬 저장 성공 ≠ 서버 보관 성공. 상태 분리
- 외부 앱 열림 ≠ 통화·구매·예매 완료. 확인 가능한 결과만 반환

## 구독·결제
- 클라이언트 보고만으로 권한 부여 금지. 플랫폼 검증된 거래·유효 상태 기준
- 체험·Pro 제한은 신규 접수에만 적용. 이미 허용된 분석의 결과 생성은 재집계 금지
- 이용량 = 접수 시 대표+구성 수만큼 예약, 분석 실패 시 반환, 같은 사진 버전 재분석 미차감. 체험은 기기·계정 양쪽 기록 (ADR-0021)
- 결과를 만든 체험 칸은 사진 삭제·교체와 관계없이 반환 안 함 (ADR-0024)
- 구매·복원 직후 = 서버가 RevenueCat REST로 즉시 재조회. RevenueCat 장애로 갱신 미확인 = 확인될 때까지 Pro 유지 (FR-B-05 확인된 만료만 제한). `TRANSFER` = 넘겨준 계정 권한 제거·받은 계정 권한 부여, 계정 데이터는 이동 없음 (ADR-0024)
